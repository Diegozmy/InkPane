# 架构说明

## 总体结构

前后端完全分离，通过 HTTP + JSON 通信，共享同一份字段约定（前端 `web/src/types.ts`
与后端 `server/src/domain/types.ts` 手工镜像，接口改动会在类型检查阶段暴露）。

```
┌─────────────────────────────┐         ┌──────────────────────────────────────┐
│  web/  (React 18 + Vite)    │         │  server/  (Express + node:sqlite)    │
│                             │  HTTP   │                                      │
│  views/      页面编排        │ ──────► │  modules/   路由 → 服务 → 仓储         │
│  components/ 视图与组件      │  /api   │  domain/    重复引擎 / 时区 / 校验     │
│  api/        React Query     │ ◄────── │  db/        连接 / 迁移 / 行映射       │
│  store/      客户端状态      │  JSON   │  http/      错误 / 中间件 / 日志       │
└─────────────────────────────┘         └──────────────────────────────────────┘
                                                        │
                                                  SQLite (data/inkpane.sqlite)
```

开发期 Vite 把 `/api` 代理到 `127.0.0.1:4000`，因此浏览器侧只有同源请求，不涉及预检；
生产模式可以直接由后端托管 `web/dist`（`SERVE_STATIC=true`）。

## 后端分层

| 层 | 位置 | 职责 | 约束 |
| --- | --- | --- | --- |
| 路由 | `src/modules/*/routes.ts` | 解析参数、调用服务、序列化响应 | 不写业务规则，不碰 SQL |
| 服务 | `src/modules/*/service.ts` | 业务规则、事务边界、领域校验 | 不拼 SQL，不依赖 Express |
| 仓储 | `src/modules/*/repository.ts` | SQL 读写、行 ↔ 实体映射 | 不含业务判断 |
| 领域 | `src/domain/` | 重复规则引擎、时区换算、Zod 校验模式 | 纯函数，可独立测试 |
| 基础设施 | `src/db/`、`src/http/`、`src/lib/` | 连接、迁移、语句缓存、错误与日志 | 与具体业务无关 |

服务层不接收 Express 的 `Request`，只接收已经校验过的 DTO，因此同一段业务逻辑既能被
HTTP 路由调用，也能被命令行脚本（`db:seed`、`db:reset`）复用。

### 请求生命周期

```
请求
 └─ helmet（安全响应头 + CSP）
 └─ securityHeaders（Cache-Control / Referrer-Policy）
 └─ cors（白名单校验）
 └─ express.json（体积上限）
 └─ requestContext（分配 requestId 并回写响应头）
 └─ accessLog（只记录写操作、慢请求与错误，避免轮询刷屏）
 └─ 业务路由（Zod 校验 → 服务 → 仓储）
 └─ notFoundHandler / errorHandler（统一错误体）
```

所有错误都收敛成同一种响应体：

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "请求数据校验未通过",
    "details": [{ "path": "color", "message": "颜色必须是 #RRGGBB 形式", "code": "invalid_string" }],
    "requestId": "3f2c…"
  }
}
```

`requestId` 同时出现在响应头 `X-Request-Id` 与错误体中，前端报错时可以直接对照服务端日志。

## 数据模型

```
categories ──1:N──► events ──1:N──► event_overrides
```

- **`events`**：日程主记录。`rrule` 字段以 JSON 保存重复规则，`null` 表示不重复。
- **`event_overrides`**：按 `(event_id, occurrence_key)` 唯一，保存「某一次实例」的
  单独修改或取消。`occurrence_key` 是**该实例在原始序列中的开始时刻**，
  因此即使实例被改期，仍然能准确指回它所属的那一次。
- 删除分类时通过 `ON DELETE SET NULL` 把关联日程置为「未分类」，不会级联删除日程。
- 删除日程时通过 `ON DELETE CASCADE` 一并清理它的实例覆盖记录。

索引覆盖了实际查询路径：`events(start_at)`、`events(category_id)`、`events(status)`、
`event_overrides(event_id, occurrence_key)`。

### 结构版本管理

迁移写在 `src/db/migrations.ts` 的数组里，用 SQLite 内置的 `PRAGMA user_version`
记录当前版本。每个迁移在事务中执行，失败自动回滚。启动时自动执行，也可以
`npm run db:migrate` 手动触发。

## 重复日程引擎

这是后端最核心的部分（`src/domain/recurrence.ts`），实现要点：

**按墙上时间生成、按瞬间输出。** 规则先在事件自身时区下生成「日期序列」，
再把每个日期与序列的起始时刻组合成瞬。因此每周三 09:00 的日程跨越夏令时切换后
仍然是当地 09:00，而不是 08:00 或 10:00（已有专门测试覆盖）。

**与 RFC 5545 对齐的边界语义**

| 场景 | 行为 |
| --- | --- |
| `count` | 从序列首个实例开始计数，被取消的实例同样占一个名额 |
| `until` | 闭区间；给纯日期时表示「包含当天」 |
| WEEKLY + `byWeekday` | 以周一为一周起点；首周里早于起始日的星期会被跳过 |
| MONTHLY 遇到不存在的日 | 跳过该月（1 月 31 日不会顺延到 3 月 3 日） |
| YEARLY 2 月 29 日 | 非闰年跳过 |

**性能与安全护栏。** 生成器按需产出日期，遇到 `count` / `until` / 查询区间上界立即停止；
另外有 `maxIterations`（默认 5000）与单次查询实例上限（`maxOccurrencesPerQuery`），
异常规则不会把服务打满。查询区间本身也限制在 400 天以内。

**重叠判定。** 与查询区间「相交」即返回，而不是要求完全落在区间内，
因此跨天事件在被查询到的那一天不会凭空消失。

### 实例覆盖的合并顺序

```
生成候选实例 → 应用覆盖（取消 / 改期 / 改内容）→ 与查询区间求交 → 过滤 → 排序
```

顺序很关键：覆盖必须在求交之前应用，否则「被改期到区间外」的实例会因为原键落在区间内
而被错误地显示出来（有测试覆盖这一场景）。

### 序列拆分（此后所有）

拖拽或编辑选择「此后所有」时，服务端在一个事务里完成：

1. 创建「新的一段」：复制主记录，起始时间改为用户拖到的时间，规则沿用
2. 把 `occurrence_key >= 拆分点` 的覆盖记录迁移到新记录
3. 把原记录的 `until` 截断为「拆分点的前一天」
4. 若拆分点就是首个实例，原序列会变成空序列，此时直接删除原记录

如果原规则是 `count` 而非 `until`，会用 `seriesIndexBefore()` 算出拆分点之前已经发生的
次数，把剩余次数写到新记录上，保证总数不变。

## 时区策略

| 数据 | 存储形态 | 理由 |
| --- | --- | --- |
| 定时事件 | ISO-8601 UTC 瞬间 | 绝对时刻，跨时区查看不会错位 |
| 全天事件 | `YYYY-MM-DD` | 纯日历日，任何时区下都是同一天 |
| 事件时区 | IANA 名称 | 重复规则按此展开，创建时取浏览器时区 |

时区换算不依赖任何第三方库：`src/domain/time.ts` 用 `Intl.DateTimeFormat` 计算某瞬间
在某时区的偏移，再用两次偏移修正把「墙上时间」还原成瞬间，可正确处理夏令时切换当天的
边界（当天有 23 小时或 25 小时）。这条路径有独立测试。

**日期串绝不经过 UTC 往返。** 全天事件的 `startAt` 在整条链路上都保持
`YYYY-MM-DD` 形态，因此 `America/New_York` 的用户新建 6 月 2 日的全天日程，
不会因为 UTC 零点换算变成 6 月 1 日。

## 前端架构

### 状态划分

| 类型 | 存放位置 | 说明 |
| --- | --- | --- |
| 服务端数据 | React Query | 日程实例、分类、统计、健康状态 |
| 跨组件 UI 状态 | Zustand（持久化） | 筛选条件、主题、提醒开关、轻提示队列 |
| 页面定位状态 | URL 查询参数 | 视图与焦点日期（`/calendar/week?d=2025-06-02`） |
| 组件内部状态 | `useState` | 弹窗开关、表单草稿、拖拽预览 |

视图与日期放进 URL，刷新、分享链接、浏览器前进后退都能保持同一状态。

### 服务端数据的失效策略

所有写操作成功后统一失效 `occurrences` / `summary` / `events` 三组缓存。
拖拽改期额外做了乐观更新：松手瞬间就地改写缓存，失败则回滚并提示，
因此拖拽不会有「松手后卡一下」的观感。

列表查询使用 `placeholderData: keepPreviousData`，切换月份时保留上一次结果，
网格不会闪空。

### 拖拽实现

不引入拖拽库，两种视图用两种原生机制：

- **月视图**：HTML5 Drag and Drop（`draggable` + `dragover` + `drop`），跨天移动最直接
- **周 / 日视图**：Pointer Events 手写。在 `window` 上监听 `pointermove` / `pointerup`，
  指针移出网格甚至移出窗口都不丢事件；用 `getBoundingClientRect()` 把纵坐标换算成分钟数，
  再做 15 分钟吸附

拖拽状态保存在 `useRef` 中，监听器只在「开始拖拽 / 结束拖拽」时绑定与解绑一次，
不会在每次 `pointermove` 时重新注册。整个过程只更新本地预览，`Esc` 可随时放弃。

### 重叠事件的列布局

`layoutTimedEvents()` 是纯函数：把当天事件按开始时间排序，逐个划入「时间簇」，
簇内用贪心策略分配列（找第一个已结束的列，否则新开一列），簇内列数决定横向宽度。
输出被换算成 CSS 变量（`--block-top`、`--block-width` 等），
位置全部通过 `calc(var(--minute-height) * N)` 表达，因此响应式改变行高时无需重新计算。

该函数有 7 项单元测试覆盖不重叠、部分重叠、被长事件包住、跨夜裁剪等情形。

### 样式组织

| 文件 | 内容 |
| --- | --- |
| `styles/tokens.css` | 设计令牌（颜色、字号、间距、圆角、动效、日历几何），含亮/暗两套 |
| `styles/base.css` | 重置、排版、焦点可见性、滚动条、减少动效 |
| `styles/components.css` | 按钮、表单、标签、浮层、反馈 |
| `styles/layout.css` | 应用外壳、顶栏、侧栏、抽屉、底部标签栏 |
| `styles/calendar.css` | 月网格、时间网格、议程视图、事件块 |
| `styles/panels.css` | 侧栏卡片、详情面板、筛选与设置 |

没有使用 CSS-in-JS 或原子化框架：日历的定位逻辑高度依赖 CSS 变量与 `calc()`，
手写 CSS 反而是表达力最强、运行时开销最低的选择。

### 密度策略

密度取向是「舒适优先」，而不是「一屏塞下最多信息」：

- 视觉密度由 `tokens.css` 一处控制：字号（正文 15px）、控件高度（42px）、
  时间轴每小时高度（72px）都集中在令牌里，改一处即可整体缩放
- **月视图不做静态配置，而是按实测高度自适应**：`MonthView` 用 `ResizeObserver`
  量出单元格真实高度，按高度模型（固定开销 62px，每条事件占 36px）算出能舒适容纳的条数。
  当「还有 N 项」按钮会挤掉一条事件时，改为不渲染按钮，用日期右侧的「N 项」计数
  与「点击当天进入日视图」来承载剩余信息
- **视口高度分档**：`calendar.css` 用 `max-height` 媒体查询逐级降低月网格行高
  （168 → 152 → 132 → 116px），尽量让整月一屏看完；实在放不下时月面板内部滚动，
  而不是把事件压扁
- `ResizeObserver` 缺失时（如 jsdom 测试环境）自动退回按 `chipsPerDay` 显示，
  因此该组件可以脱离真实布局被单元测试

## 课程同步（对接学校课程管理系统）

`server/src/modules/courses/` 负责把学校课表变成日历里的每周重复日程。

### 为什么需要「先取页面再登录」

学校系统的登录页每次加载都会**随机下发**一对 AES `key` / `iv` 并写在页面内联脚本里：

```js
var privateKey = 'bdijlmALZ@[}=,;:';   // 每次刷新都不同
var privateIv = 'hmpqwBEFM126$<?|';
```

因此登录无法只发一个请求，必须三步走：`GET 登录页 → 解析当次密钥 → 加密后 POST`，
且三步共用同一个 `PHPSESSID`。这个过程没有第三方库能代劳，只能按官网前端的实现逐字节复刻，
所以 `client.ts` 里带了一个轻量 Cookie 容器与手动重定向处理。

### 两个已经踩过的坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 返回「请输入账号！」 | 用了硬编码密钥（页面每次随机下发） | 每次登录都重新取页面解析密钥 |
| 返回「账号不存在或者密码错误」 | 对密码做了 URL 编码，而服务端只按 `&`、`=` 手工切分且不 urldecode | 原样拼接，并在密码含 `&`/`=` 时提前给出可操作提示 |
| 返回「非法请求！」 | 业务接口只接受 POST | 所有业务请求走 POST 并带 `X-Requested-With` |

### 课表结构

`POST /Xskebiao` 返回 JSON，真正的表格在 `info.html` 里：

```
<tr><td></td><td>星期日(2026-10-11)</td><td>星期一(2026-10-12)</td> … <td>星期六(2026-10-17)</td></tr>
<tr><td>第一节</td><td></td><td><span><div>高三语文1-1</div><div>朱英杰</div><div>301</div></span></td> … </tr>
```

即：第 0 列是节次，第 1–7 列是**星期日到星期六**（注意不是周一到周日），
单元格内依次是课程名 / 教师 / 教室；表头通常带真实日期。

`parser.ts` 据此解析，并额外处理：中文数字节次（`第十一节`）、`colspan` 导致的列偏移、
无表头时按「第 1 列 = 周一」兜底、整表无节次时明确报错而不是静默返回空。

### 时间从哪来

学校系统只给「第几节」，不给时间。所以「每节课起止时间」必须由用户配置，
并且按需求支持**周五使用一整套独立时间表**（`fridaySeparate` + `fridayPeriods`）。
出现未配置的节次时按每节 50 分钟顺延估算，并在预览里标注「时间估算」提醒补齐。

### 幂等与差量

```
课表条目 (学程, 星期, 节次)
   ↕ course_slot_links (source, external_key → event_id)
本地日程
```

导入时按 `external_key` 查映射：命中则更新、未命中则新建；课表里消失的条目删除映射与日程。
因此同步可以用任意频率反复执行，不会产生重复数据，也不怕中途失败（整段在事务里）。
用户在日历上拖动某次课属于「仅此一次」的实例覆盖，同步只更新主记录，不会覆盖这类改动。

### 凭据存储与安全边界

密码以 **AES-256-GCM** 密文写入 `sync_credentials`，密钥保存在 `data/.sync-key`
（创建时尽力设为 `0600`）；明文只在请求生命周期内存在于内存，不写日志、不进数据库，
接口只回传 `username` 与脱敏的 `passwordMask`。

必须说清楚这个方案**防得住什么、防不住什么**：

- 防得住：数据库文件被单独拷走（没有密钥文件解不开）
- 防不住：已经能以你的身份读本机文件的攻击者，因为密钥就在同一台磁盘上。
  要做到后者需要操作系统级密钥保管（Windows DPAPI / macOS Keychain），
  那需要原生模块，与本项目「零原生依赖」的取舍冲突，因此不承诺该强度。
- 另外：学校系统本身是 **HTTP 明文站点**，账号密码在到达校方服务器时不受传输加密保护。
  这是校方系统的限制，应用内已明确提示；能改的只有在校内门户定期更换密码。

### 自动同步调度

不引入任务队列，只用一个分钟级定时器：每次 tick 才读取设置，因此改开关/间隔立即生效；
用运行中标记防止并发；失败只记日志并等下一周期重试，不会破坏已有日程。
`setInterval` 与启动延时都 `unref()`，不会阻止进程退出。

## 多用户与多设备（v4）

### 账户模型

- `users`：用户名（NOCASE 唯一）、scrypt 密码哈希、`role`（admin/user）、`status`。
- `sessions`：只存会话令牌的 SHA-256，HttpOnly Cookie 下发；30 天有效，可撤销。
- `devices`：每台硬件一行，存令牌哈希与遥测；设备令牌解析出 `user_id` 后再组装屏幕。
- 初始化：迁移会创建一个 `pending_setup` 管理员；`/api/setup` 认领后变为活跃管理员。
  之后账号只能由管理员创建，不开放自助注册。

### 租户隔离

所有用户数据表（`categories` / `events` / `todos` / `app_settings` / `weather_cache` /
`sync_credentials` / `course_slot_links` / `sync_runs` / `devices`）都带 `user_id`。
仓储函数显式接收 `userId`，所有 SQL 带 `WHERE user_id = ?`；跨用户的 `:id` 一律 404。
实例覆盖（`event_overrides`）通过已校验归属的 `event_id` 访问。

### 显示与天气

- 布局、刷新间隔、时区都按用户保存在 `app_settings`，同一用户的设备共用。
- 设备拉屏仍只读该用户的天气缓存；后台天气调度器每 15 分钟按用户刷新，
  避免“控制台没打开时天气永远不更新”。
- 时区写入 `display.timezone`，所有“今天/月历/待办到期/课程导入”都使用用户时区。

### 课程同步

- 凭据、设置、映射与同步记录按用户隔离。
- `sync_credentials.base_url` 记录凭据对应的学校地址；地址变更后旧密码不再被使用，
  必须重新输入，避免把已保存密码发往新地址。
- `remember=false` 只写入进程内 12 小时缓存，不落库。

### 设备令牌

- 完整令牌只在创建/轮换时返回一次；数据库只存 SHA-256 与前 4/后 4 位前缀。
- 旧版单例 `device.token` 在 v4 迁移时哈希后写入 `devices`，旧固件无需改配置即可继续拉取。
- `GET /api/device/screen`、`POST /api/device/telemetry` 只认 `X-Device-Token`；
  控制台设备管理走 `/api/devices`（会话鉴权）。

## 已知取舍

- **单机/局域网部署，不内置 TLS。** 管理接口已要求登录；跨网访问请在前面加 HTTPS 反向代理。
- **管理员不能读取用户内容数据。** 用户管理只返回账号元数据与设备数量。
- **每个用户一套布局。** 若未来需要每设备独立布局，新增 `device_settings` 覆盖层即可。
- **重复日程的查询在应用层展开。** 没有把展开结果物化成表。个人规模（数百到数千条日程）
  下性能充裕，且避免了「规则改了要重算物化表」的一致性问题。若数据量增长到十万级，
  应改为查询时按需物化或引入展开缓存。
- **编辑重复实例只提供「仅此一次 / 整个序列」两档。** 表单里对「此后所有」的语义容易
  产生歧义（改内容还是改时间），因此把「此后所有」放在拖拽与删除这两个语义明确的入口，
  表单里只保留另外两档。
- **提醒靠前端轮询而非服务端推送。** 免去了 WebSocket 与推送证书，代价是页面必须处于
  打开状态。对于需要「关掉页面也能收到提醒」的场景，应改为服务端调度 + Web Push。
- **`node:sqlite` 在部分 Node 版本仍标记为实验特性。** 建议使用 Node 22.13+ 或 24 LTS；
  若要完全规避实验特性，把 `src/db/client.ts` 换成 `better-sqlite3` 即可。
